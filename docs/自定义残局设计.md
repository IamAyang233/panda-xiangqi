# 自定义残局 · 设计（已实现）

状态：**已实现**（2026-09-23，随 2.0.5 发布）。本文件 §1-§2 的分析仍然有效；
§3/§4 是当时的草案，**与最终实现有一处重要偏差**（见 §8），实施以代码与
`docs/protocol.md` v2 为准。§5 的待拍板项已全部拍板，结论见 §5。
原始草案基于 HEAD `8dd4e7b`，其中引用的行号已过期，不要照它改代码。

背景：用户要「在残局里增加自定义残局，自己摆残局挑战」。上一版 grill-me 访谈结论随会话压缩丢失，未落盘；本版基于当前代码（HEAD `8dd4e7b`）重新推导，结论即时写入本文件。

## 1. 目标

大厅提供一个入口：用户摆好局面 → 设定执子方 / 先手 / 目标 / AI 档位 → 进入挑战。挑战过程与既有残局完全一致（守方引擎应着、可悔棋 / 提示 / 重开、目标判定同规则）。

## 2. 现有架构可复用点（逐条核对代码）

| 环节 | 现状 | 结论 |
|---|---|---|
| 残局数据 | `puzzle.Puzzle{FEN, PlayerSide, Goal, ParMoves, Solution}`（`puzzle.go:14`） | 自定义残局只需构造一个临时 Puzzle |
| 建局面 | `NewSession` 用 `ParseFEN(pz.FEN)`，失败回落满盘（`session.go:84`） | 自定义 FEN 直接可用 |
| 正解校验 | `solutionMoveAt` 在无 Solution 时返回 `""`；`ApplyPlayerMove` 只在 `want != ""` 时判偏离（`session.go:285`） | `Solution=nil` → 不触发偏离，任意合法着法都算正常 |
| 守方应着 | `aiReply` 中 `solUCI == ""` 落到 `default` → `engines.BestMove`（`session.go:420,442`） | 守方自动由引擎应着，无需新代码 |
| 目标判定 | `finishLocked`：`Goal=="draw"` 判和，否则判玩家将死 / 困毙（`session.go:361-368`） | 直接复用 |
| 重开 | `Restart()` 用 `pz.FEN` 恢复（`session.go:671`） | 重开回到用户摆的局面 |
| 提示 | `Hint()` 无正解时回落引擎建议（`session.go:614`） | 直接可用 |
| 异常兜底 | AI 出着非法 → 改走首个合法着法；无合法着法 → 正常判结束（`session.go:457-468`） | 非法局面不会卡死进程 |

**必须改的只有 3 处**：

1. `puzzleLevel()`（`session.go:505`）按 `pz.Difficulty` 映射引擎档位，自定义残局会落到 `default` 固定为 9 档 → 加分支：Difficulty 为空时用玩家选的 `s.Level`。
2. `finishLocked()` 星级（`session.go:377-385`）：`ParMoves=0` 时 `playerMoves <= 0` 恒假 → 落到 `else` 误给 2 星 → 加 `ParMoves > 0` 前置条件，自定义残局不评星。
3. `web/js/board.js` 只有 `parseFEN`（`board.js:13`），**缺 `boardToFEN`**（Map → FEN）——摆棋器提交时需要。

## 3. 后端改动

- `createGameReq` 加 `Fen string`（`api.go:124`）。
- `handleCreateGame` 的 `case session.ModePuzzle`：`req.Fen != ""` 时不查题库，改构造临时 Puzzle：

  ```go
  pz = &puzzle.Puzzle{
      ID: "custom", Name: "自摆残局", FEN: req.Fen,
      PlayerSide: req.Side, Goal: req.Goal,
      ParMoves: 0, Solution: nil, Difficulty: "",
  }
  ```

- **服务端必须校验 FEN**（否则前端可绕过校验把非法局面喂给引擎）。四条硬校验：
  1. `ParseFEN` 成功（已覆盖 10 行 / 字符合法 / 行长）
  2. 双方各恰好 1 个将 / 帅
  3. 将帅不照面
  4. 先走方至少有一个合法着法（`LegalMoves(Turn)` 非空）

  任一条不满足 → HTTP 400 并回具体原因。

## 8. 实施结果与和草案的偏差

**最大偏差：没有走「临时 FEN 开局」那条路。** 草案 §3 打算给 `createGameReq` 加 `fen`
字段、为自摆局合成临时 Puzzle；实际实现改成 **先保存落盘、再按 id 挑战**，于是
`createGameReq`、`handleCreateGame` 的残局分支、`Session`、`Restart` **一行都不用改**，
只有一处必须改：残局分支的查找要走 `lookupPuzzle`（题库 + 自定义库），
否则「保存并挑战」会 404 —— 这个缺陷被端到端黑盒实测抓到，已补单测钉住。

代价：必须先存再玩（不能玩完再决定要不要留）。收益：只有一条代码路径。

其余落地情况：

- **四条硬校验**照草案原样实现（服务端唯一防线），客户端另做同口径预检并逐条提示缺什么。
- **3 处必改点全部落实**：`puzzleLevel` 空/未知难度改用玩家档位（并把「大师」写成显式分支）；
  `finishLocked` 星级加 `ParMoves > 0` 前置；`board.js` 补 `boardToFEN`（与 `parseFEN` 严格互逆，
  已用 4 个固定 + 300 个随机局面验证）。
- **草案没提到的两个坑，实施时发现并修掉**：
  1. `game.js` 的逐层返回按 `mode === 'puzzle'` 判定，自摆局退出会跳到**内置残局列表**；
     改为按是否为自摆局区分去向。**去向本身在 2026-09-23 按用户实测反馈又改过一次**：
     一开始让自摆局回大厅（理由是它没有「关卡序列里的位置」），但用户从「残局挑战 →
     自定义」点进去挑战、退出却被丢回大厅，位置和筛选都丢了 —— 现在统一回残局列表，
     并主动把页签切到「自定义」（`puzzles.js` 导出 `selectDiff`，`main.js` 的
     `onExitToPuzzles(diff)` 接上）。
  2. 前端原先用「有没有 `stars`」反推残局是否通关，而自摆残局不评星 → **赢棋显示成挑战失败**。
     改为服务端在 `game_over` 里显式下发 `cleared`，前端不再复刻判定逻辑。
- **落盘目录刻意独立**（`custom` / `QIJING_CUSTOM`）：
  内置题库目录 `puzzles` 是「整体替换内嵌题库」，写进去会弄丢 3576 关。
  默认位置按「显式配置 ＞ 框架目录 ＞ 相对路径」解析：飞牛上未配置时落在
  `TRIM_PKGVAR/custom-puzzles`（即 `/vol{n}/@appdata/panda-xiangqi/custom-puzzles`，
  在数据卷上，升级替换应用目录不会带走），本地运行则是 `./custom-puzzles`。
- **已知代价（删除）**：全服共享且应用内无账号体系（fnOS 网关统一鉴权），
  因此任何访问者都能删除自摆残局，二次确认是唯一防线。不做批量清空（避免误删一大片）。

## 6. 已知代价与风险

- 摆到一半刷新页面会丢（与「不持久化」决策一致；不做 sessionStorage 草稿）。
- 自定义残局没有正解，「提示」语义从「提示正解」变为「引擎建议的应着」。
- 服务端校验是唯一防线；若跳过，非法局面会让引擎返回错乱着法（实测不会崩进程，但语义无意义）。

## 7. 验证计划

- **Go 单测**：双帅 / 缺帅 / 将帅照面 / 先走方无着法 四种非法 FEN 均返回 400；合法 FEN 建局成功，且 `Solution=nil` 时玩家任意合法着法都不触发 `deviate`。
- **前端几何断言**：摆棋器点击放置 / 删除 / 撤销，沿用 `loader-check.html` 的同源 iframe 驱动方式。
- **端到端**：摆一个简单杀局 → 开始挑战 → 一步将死 → 判胜且 `game_over` 无 `stars` 字段。

## 9. 卸载时的数据归属（2.0.5 补）

自定义残局落在数据卷上，所以**卸载本来就不会带走它们**；要做的是「用户明确想清空时才清」。
飞牛的应用包支持原生卸载向导（`wizard/uninstall`），于是这条链是：

| 环节 | 位置 | 行为 |
| --- | --- | --- |
| 询问 | `fnos/panda-xiangqi/wizard/uninstall` | 单选「保留（推荐）」/「删除全部自定义残局」，字段 `wizard_keep_data`，默认 `keep` |
| 执行 | `fnos/panda-xiangqi/cmd/uninstall_init` | 值为 `delete` 才删；其余一律保留并在 `$TRIM_PKGVAR/app.log` 记一行 |

三个刻意选择：

1. **放在 `uninstall_init`**：数据目录是 `${TRIM_PKGVAR}`（`/var/apps/panda-xiangqi/var`
   → `/vol{n}/@appdata/panda-xiangqi`）。框架移除已装文件之后这条软链就没了，
   `uninstall_callback` 阶段再解析不出路径；`init` 阶段一切完好。
2. **删哪条路径按应用同一口径解析**：`${TRIM_APPDEST}/server/config.yaml` 的 `custom` 项
   → `QIJING_CUSTOM` → `TRIM_PKGVAR/custom-puzzles`。不这么做的话，用户把 `custom`
   指到数据卷某个目录后，向导里选「删除」删的会是那个没人用的默认目录 —— 点了删除却没删。
3. **默认方向是「留」**：脚本只在取值明确落在删除集合（`delete|del|remove|clear|no|false|0`）
   时才动手；向导变量缺失、老客户端不传、`appcenter-cli` 卸载…全部保留。
   另外三道守卫阻止误删：目标是符号链接不删、目录里混有非残局文件不删（用户可能把
   `custom` 指到共享目录）、解析不出路径不删。宁可留一坨数据，不可误删别的东西。

关于页**不写**这段说明：卸载向导本身就是飞牛原生表单，用户卸载时自然会看到，
在应用内再复述一遍只会变成过期文案。
